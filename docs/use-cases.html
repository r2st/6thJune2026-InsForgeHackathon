Hush · use cases · built on InsForge

Where Hush earns its keep.

One job: catch the backend bugs that return 200 and still break your customer — then ship the policy fix.

Each case is the same loop: watch → correlate → diagnose → fork & test → fix & ship
00 · The shape of the problem

All of these fail at the policy layer, not the code path.

A request comes in. The server runs. It returns 200 OK. But the wrong rows came back — too few, too many, or someone else's. Nothing throws, so your error tracker stays silent. The only signal is a frustrated user on the frontend and a quiet decision in the backend logs. Hush correlates the two, then fixes the policy that misfired.

The use cases below are the bug classes Hush is built for, the teams that need it, and the moments you reach for it. Every one is a real insforge.toml diff — small, structured, and testable on a forked branch project before it ever reaches your repo.

01 · Bug classes it catches

Six silent bugs. One fix shape.

// vanished records

Their own data is invisible

SymptomA customer opens "My Orders." It's empty. They refresh, rage-click, give up — but the orders exist.
CauseAn over-restrictive RLS policy filters legitimate rows. Often a tenant or owner check that's too tight.
Hush shipsA one-policy insforge.toml diff that widens the predicate, proven on a branch where the rows reappear.
High confidence · single policy → open PR
// cross-tenant leak

They saw another company's rows

SymptomFor a moment, a list shows records that belong to a different tenant. The user notices before you do.
CauseA policy is missing its tenant scope, or a new route skipped the RLS check entirely. A leak, not a filter.
Hush shipsThe tenant predicate added back, with a branch replay proving the foreign rows vanish. High blast radius, so a human signs off.
Security-critical · draft PR + trace for review
// claim drift

Auth changed, the policy didn't

SymptomA whole cohort of users suddenly sees nothing — usually right after an auth or onboarding change ships.
CauseThe JWT shape moved (e.g. tenant → tenant_ids[]) but the policy still reads the old claim path.
Hush shipsA diff that reads the new claim. The branch replays the same session and the cohort gets its data back.
High confidence · single policy → open PR
// leaked file

A signed URL serves a stranger's file

SymptomA receipt or document link returns 200 but loads the wrong customer's PDF. The content is real — just not theirs.
CauseA Storage bucket policy is too open, or object paths aren't scoped to the owner.
Hush shipsA bucket-policy diff scoping access to the owner, verified against the same request on a fork.
Medium · touches storage rules → draft PR
// silent write drop

They saved it — and it's gone

SymptomA user submits a form, sees success, comes back later and the record isn't there.
CauseAn INSERT/UPDATE policy silently rejects the write while the API still returns a success shape.
Hush shipsA write-policy diff so the row commits, proven by replaying the submission on the branch project.
High confidence · single policy → open PR
// post-migration regression

A deploy quietly broke a route

SymptomA page that worked yesterday returns empty or wrong data today. No error, no alert — just a new wave of tickets.
CauseA recent migration tightened or reshaped a policy and clipped a route nobody re-tested.
Hush shipsA diff that restores the intended access, with a branch showing the route healthy again.
Medium · verify intent → draft PR

When the branch project can't reproduce the anomaly cleanly, Hush doesn't guess. It opens a GitHub issue with the session clip and the request-log diff attached — low-confidence, human's call. The action always matches the certainty.

02 · Who reaches for it

Built for anyone running multi-tenant SaaS on InsForge.

The small team with no QA

Three engineers shipping fast. No one owns the policy layer. Hush is the QA for your RLS — it watches real sessions and flags the silent leak before it becomes a postmortem.

The platform team at scale

Dozens of policies, many tenants, frequent auth changes. Hush gives every silent bug an audit row and routes the safe fixes straight to a PR, the risky ones to a human.

The security & compliance owner

"Did customer A ever see customer B's data?" becomes an answerable question. Every correlation is logged, every fix is a reviewable diff with a before/after trace — evidence, not folklore.

The on-call engineer

A ticket says "my orders disappeared" with no repro. Hush already has the session, the log, and a candidate fix waiting — triage time drops from hours to a glance.

03 · When you reach for it

Three moments in a team's week.

Every day, quietly
Hush sits behind your live app. A user gets stuck, Hush correlates and (when confident) opens a PR. The default state is a safety net you don't think about until it catches something.
Right after a migration
Auth schema or policy just changed. This is when claim-drift and regression bugs land. Hush watches the first real sessions through the new policies and flags drift before the tickets pile up. (This is where it overlaps with Migration Pilot.)
During an incident
A leak is reported. Instead of asking the user for a repro that never comes, you open the receipt page and read the symptom-to-policy trace — the failing policy and a tested fix are already there.
04 · Where Hush stays out of the way

What it deliberately doesn't do.

Being honest about the edges is what makes the rest trustworthy.

Not in scope

  • Crashes and stack traces. That's Sentry's job, and it's good at it. Hush only takes the bugs that don't throw.
  • Arbitrary app-code bugs. Race conditions, state-management bugs, CSS regressions — Hush fixes insforge.toml, not your React.
  • Anything it can't reproduce on a fork. No branch-project proof, no PR. Unreproducible anomalies become issues, never auto-fixes.
  • Changes a human rejected before. Close a PR as "by design" and Hush remembers the shape — it won't raise it again.

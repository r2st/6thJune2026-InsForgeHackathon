The map.

Six surfaces. One loop. Every box exists because the loop doesn't close without it.

01 · The loop

Capture → Diagnose → Test → Ship.

Witness is a closed-loop agent. A user gets stuck on the demo storefront. Sixty seconds later, a PR with a four-line insforge.toml diff is open on the victim repo. The session clip is embedded; the failing branch-project trace is attached.

01
Capture
rrweb · edge fn
User rage-clicks. rrweb fires. ingest edge function pulls the matching backend request-log window.
02
Diagnose
InsForge AI · pgvector
Embed (session shape + request log + RLS verdict). Dedup against prior runs. Generate the candidate TOML diff in plain English.
03
Test on a fork
Branch project · Limrun
Apply the TOML diff to a branch project. Replay the interaction. Old fails. Patched passes. Proof.
04
Ship
Devin · GitHub
Score confidence. High → PR with the diff. Medium → draft PR with the failing trace. Low → issue with the clip.
02 · The map

Six surfaces. Six wires.

Three Vercel-hosted surfaces (demo store, receipt page, GitHub PR). Three InsForge primitives (prod backend, branch project, edge functions). One external agent (Devin). Nothing else.

Orange edges are the user's path. Mint edges are Witness telling the story back. Grey edges are internal handoffs the user never sees.

04 · Why InsForge is structurally load-bearing

Four primitives. Each one the loop dies without.

Witness could not be built on Supabase, Convex, or Neon — not without re-implementing pieces InsForge gives us declaratively. These four primitives are why this product lives on this platform.

PRIMITIVE 01

Branch projects

Forks of the entire backend — schema, RLS, auth, data — in seconds. Lets Witness test a candidate insforge.toml patch against real production shape without risking prod. No other platform has this at this fidelity.

PRIMITIVE 02

Declarative insforge.toml

Schema, auth policies, RLS, edge functions — all one file. The fix becomes a 4-line diff Devin can confidently one-shot. If the backend lived in a dashboard, the fix would be untraceable.

PRIMITIVE 03

pgvector + RLS in one engine

The embedding lives in the same row as the bug. Confidence tiers, dedup, "learn from rejection" — all same-query joins, no second store, no embedding sync drift.

PRIMITIVE 04

Realtime + Storage + Edge fns, unified

One insforge.toml stands up the bus, the bucket, and the functions. The 60-second receipt-page demo is impossible if any of these three live elsewhere.

05 · Data model

Four tables. RLS on every one.

Minimal model — every column earns its row. The schema lives in insforge.toml; the demo bug lives in the orders RLS policy.

# insforge.toml — schema slice

[tables.tenants]
columns = ["id uuid pk", "name text", "jwt_claim text"]

[tables.orders]
columns = ["id uuid pk", "tenant_id uuid fk tenants.id", "user_id uuid", "total numeric", "created_at timestamptz"]
rls     = "tenant_id = auth.jwt() -> 'tenant'"   # <— the demo bug lives here

[tables.bug_runs]
columns   = ["id uuid pk", "captured_at timestamptz", "session_clip_url text", "diagnosis text", "toml_diff text", "confidence numeric", "status text", "pr_url text"]
embedding = "vector(1536)"
rls       = "tenant_id = auth.jwt() -> 'tenant'"

[tables.bug_decisions]
columns = ["run_id uuid fk bug_runs.id", "verdict text", "closed_at timestamptz", "closed_by text"]
# verdict ∈ {merged, rejected, dismissed, duplicate}

[storage.buckets.clips]
visibility = "signed"
ttl_seconds = 3600

[realtime.channels.receipt]
events = ["captured", "diagnosing", "testing", "shipped", "failed"]

Confidence tiers live in bug_runs.confidence. The learning loop reads bug_decisions.verdict and writes the result back into the next dedup query as a similarity penalty.

07 · What we are NOT building

Owning the non-goals.

Q&A defense — every one of these is intentional, not missing. If a judge asks "why didn't you do X," the answer is in this list.

  • A real session-replay capture pipeline.rrweb is shipped in the toy app. Productionizing capture across SDK quirks, ad-blockers, and CSP is out of scope. The capture is a stub the right shape; the rest of the loop is the real product.
  • A general-purpose code-fix agent.Witness only patches insforge.toml. We deliberately do not pretend Devin can one-shot arbitrary React or backend code. The narrow scope is the point.
  • Multi-tenant billing, admin UI, login.Anon-key auth on the demo storefront, hardcoded tenant IDs in the seed. The deck never claims otherwise.
  • A real customer onboarding flow.This is a pitch-day product. Buying the install path is for week two.
  • Production-grade RLS coverage.One policy is wrong, one policy is patched. Generalising the diagnosis to N policies is the second commit, not the demo.
  • Long-running runs.If a fix takes >90 s, we drop to draft-PR mode and let the dev finish. The agent's job is to start the conversation, not own it.
08 · Open questions

What's still TBD.

  • Sponsor confirmation on session capture.If Replicas is the official sponsor, we wire it in alongside rrweb. If not, rrweb-only ships.
  • Branch-project warm-boot time.Needs measuring at T+1h. If >15 s, the 60-second demo budget gets tight and we need to pre-warm the fork during the receipt-page intro.
  • AI gateway latency.InsForge AI vs direct OpenRouter — measure both. The embedding step is on the critical path.
  • Devin failure mode.If Devin can't open a PR (rate limit, auth failure), does the receipt page show "shipped" with a fallback link, or surface the failure honestly? Lean: surface honestly.

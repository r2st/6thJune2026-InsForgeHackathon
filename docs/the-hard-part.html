Hush · positioning brief · 2026-06-06

Is Capture the important part?

Short answer: no. The hard part is proving the fix without breaking production. Capture is the cheapest step in the loop. Test-on-a-fork is the one nobody else can do.

01 · The question

The loop has four steps. Which one is load-bearing?

Hush watches a session, diagnoses the silent backend bug, tests the proposed fix on a forked backend, and ships a PR. Of those four steps, exactly one is genuinely hard to replicate. The others are commodities or close to it.

01
Capture
// cost · low
rrweb + an HTTP header. Open-source, productionized by FullStory, LogRocket, Replay.io. Frustration signals (rage-click, dead-click) are detectable in <30 lines.
02
Diagnose
// cost · medium
Structured LLM call. Hard to do well; not hard to do at all. Every AI coding tool ships a version of this. The prompt quality is the differentiator, not the existence of the step.
03
Test on a fork
// cost · high · moat
This is the part nobody else can do. Forking the entire backend — schema, auth, RLS, seeded data — in seconds, replaying the failing session against it, and getting a falsifiable verdict. No competitor has this primitive at this fidelity.
04
Ship
// cost · low
Devin + GitHub API. Open a PR, attach the clip, score the confidence. Plumbing.

Pricing the steps honestly is what reveals the moat. Capture has a thousand alternatives. Devin and the GitHub API are commodities. Diagnose is just a good prompt. Test-on-a-fork has one implementation path, and it requires a primitive nobody else ships.

02 · Why Capture isn't the hard part

Three reasons the capture column is cheap.

It's been done. rrweb has been a commodity since 2018. FullStory's frustration-signal detection is published. Anyone building a session-capture SDK in 2026 is doing systems integration, not invention.

It's not the differentiator. Replay.io captures sessions. So does Sentry. So does Hotjar. They all have it. None of them ship a fix. Adding capture to a fix-loop doesn't give you the loop — capture is a precondition.

The interesting input isn't the session. It's the correlation between the session and the backend decision. The session timestamps the symptom; the backend log holds the cause. Hush's edge function does the join, but that's a lookup against an indexed column, not a research problem.

If a competitor copied our Capture step verbatim tomorrow, they still couldn't ship the fix. Because they have nowhere safe to test it.
03 · The real hard part

Proving the fix without touching production.

Every step before this one produces a hypothesis — the user expected X, the failing policy is Y, the fix is Z. Hypotheses can be wrong. To ship them as a PR you need proof, and the only way to get proof is to actually run the patched system against the actual failing input.

That's a tractable problem only if you can fork the entire backend — schema, RLS, auth, seeded data — in seconds. And then re-fire the captured request against the fork with the user's real claims. And then compare the verdict against prod.

This is what we mean by test on a fork. It is the structural problem Hush solves, and it is the structural reason Hush exists on InsForge.

Two independent signals. Prod fails → the bug is real. Fork passes → the fix is real. Both are required before Hush opens a PR. If only one fires, the run drops a confidence tier.

05 · How we solve it uniquely

Four moving parts. None of them are Capture.

The Test step is built out of four pieces. Each is small. Together they're the unique system.

PIECE 01

Branch projects as ephemeral test sandboxes

InsForge forks the entire backend — schema, RLS, auth, seeded data — in <2s. We pre-warm a pool of two so the demo never waits on a cold spin-up. The fork burns when the test ends.

PIECE 02

JWT forging against the fork's signing key

The captured JWT is signed by prod and won't validate on the fork. We re-sign the same claims with the fork's key. That means the policy receives the user's real claim shape — which is the whole reason the bug exists.

PIECE 03

Parallel replay → falsifiable verdict

We fire the captured request at prod (unchanged) and the fork (patched) in parallel. The verdict is two independent signals: prod returns 0 rows; fork returns the expected 3. Either signal alone proves nothing. Both together prove everything.

PIECE 04

Verdict gates the confidence score

If the fork doesn't pass, confidence caps at 30 — Hush opens an issue, not a PR. The replay verdict is the single strongest signal in the score. No replay, no PR. Ever.

Each piece is small. None is the moat by itself. The system is the moat — and the system runs because branch projects exist and `insforge.toml` makes the fix a declarative 4-line diff. Both are InsForge primitives. Neither is replicable in a competitor's substrate.

What we'd say to a technical judge.

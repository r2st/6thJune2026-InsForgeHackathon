00 · How to read a case file

Symptom on the screen, cause in the policy.

These are the bugs your error tracker can't see — the request ran, the server answered 200, and the wrong rows came back. The only evidence is a frustrated user on the frontend and a quiet RLS decision in the backend log. Hush links the two and proves the fix on a forked branch before it opens a PR.

Every example below is a real insforge.toml diff — one policy, a handful of lines — with the branch-replay row counts that confirmed it. Companies are illustrative; the bugs and the fixes are exactly the shapes Hush handles.

01 · The canonical one

Worked examples.

CASE-01 · claim drift · b2b billing SaaS "Ledgerly"

The whole finance team lost their invoices overnight.

Opened PR

An SSO migration shipped Thursday. Friday morning, everyone at three customer accounts opens Invoices and sees an empty table. They refresh, they re-login, they file tickets that all say "your app is down." It isn't. The invoices are right there in the database.

// signal
3× rage-click on "Reload", then tab closed. 09:14.
// user saw
"No invoices yet." — expected 8 rows, got 0.
// monitoring saw
200 OK, 38ms. No error. Sentry green.

Root causeThe SSO change moved the tenant claim from org to org_ids[]. The policy still reads the old claim path, so auth.jwt() ->> 'org' is null and every row is filtered out.

# insforge.toml · tables.invoices.rls
- rls = "tenant_id = (auth.jwt() ->> 'org')::uuid"
+ rls = "tenant_id = (auth.jwt() ->> 'org')::uuid OR tenant_id = ANY((auth.jwt() -> 'org_ids')::uuid[])"
prod 0 rows fork 8 rows confidence 94% single policy · 1 table rage-click → PR in 41s
CASE-02 · silent write drop · helpdesk SaaS "Tendril"

Support replies vanished the moment agents reloaded.

Opened PR

An agent types a reply, hits send, sees the "Sent" toast, moves on. The customer never gets it. The agent reopens the ticket an hour later and the reply isn't there — so they type it again, and again. The API said success every time.

// signal
Same reply submitted 3× in 4 min — duplicate-submit pattern.
// user saw
"Sent ✓" toast, then an empty thread on reload.
// monitoring saw
201 Created shape returned. Zero rows actually committed.

Root causeAn auth rename left the INSERT policy checking author_id against a claim that's now null, so the write is silently rejected by RLS while the endpoint still returns a created-shape body.

# insforge.toml · tables.messages.insert
- insert = "author_id = (auth.jwt() ->> 'uid')::uuid"
+ insert = "author_id = auth.uid()"
prod write rejected fork write committed confidence 91% single policy · 1 table dead-state → PR in 52s
CASE-03 · cross-tenant leak · HR platform "Rosterly"

A manager glimpsed another company's employees.

Draft PR + human sign-off

A manager at Company A types into the people-search box. For a flash, the dropdown shows names from Company B before the UI re-renders. They screenshot it and email security. This is the one bug where being fast and careful both matter.

// signal
Manual "Report a problem" with screenshot attached.
// user saw
Foreign tenant's employees in a search result.
// monitoring saw
200 OK. A leak never throws — it just over-returns.

Root causeA new /directory/search query path was added against employees without a tenant predicate — its policy evaluates to true, so it returns across tenants.

# insforge.toml · tables.employees.select
- select = "true"
+ select = "tenant_id = (auth.jwt() ->> 'tenant')::uuid"
prod cross-tenant fork own tenant only confidence 88% high blast radius → human tightening access · never auto-merged
CASE-04 · leaked file · e-commerce "Cartwheel"

A receipt link opened a stranger's order PDF.

Draft PR (touches storage)

A shopper clicks "Download receipt." The PDF loads — but it's someone else's order, with someone else's name and address. The link works perfectly. That's the problem.

// signal
Rapid back-button + re-click; then support chat opened.
// user saw
A valid PDF belonging to a different customer.
// monitoring saw
200 OK from Storage. Correct file served — to the wrong person.

Root causeThe receipts bucket read policy was left open during launch and never scoped to the owner, so any authenticated user can fetch any object path.

# insforge.toml · storage.buckets.receipts.read
- read = "true"
+ read = "(storage.foldername(name))[1] = auth.uid()::text"
prod any file fork owner only confidence 86% storage rule → draft PR report → trace in 9s
CASE-05 · post-migration regression · analytics SaaS "Pulse"

Every analyst's dashboard went blank after a deploy.

Draft PR (verify intent)

A migration tightened a role check on Tuesday. By Wednesday, analysts open their dashboards to empty charts. Admins are fine, so it slips past the smoke test. The tickets say "no data" — which reads like a pipeline outage, not a policy.

// signal
Dead-clicks on chart filters; reloads; tab abandoned.
// user saw
"No data for this range" on every chart.
// monitoring saw
200 OK, empty arrays. Looks like an empty range, not a bug.

Root causeThe migration added role = 'admin' to the events select policy, clipping the analyst role that legitimately needs read access.

# insforge.toml · tables.events.select
select = "account_id = (auth.jwt() ->> 'account')::uuid
- AND role = 'admin'"
+ AND role IN ('admin', 'analyst')"
prod (analyst) 0 rows fork (analyst) 1,204 rows confidence 83% restores intent → review caught on first post-deploy session
CASE-06 · can't reproduce · marketplace "Stallpoint"

The intermittent empty cart — where Hush refuses to guess.

Opened issue, no auto-fix

A seller's listings sometimes show zero, sometimes show all. It correlates with traffic, not with any one user. Hush forks the backend, replays the failing request — and the fork returns rows too. No clean reproduction means no PR. Hush does the honest thing.

// signal
Rage-clicks, but on only ~1 in 20 page loads.
// user saw
Listings present, then gone, then back.
// monitoring saw
200 OK throughout. The policy isn't the smoking gun.

OutcomeProd and fork both return rows on replay — the anomaly likely lives in a read-replica lag or cache, not in insforge.toml. Hush opens a GitHub issue with the session clip and the request-log diff attached, and stops. No proof, no PR.

prod 12 rows fork 12 rows confidence 34% no reproduction → issue clip + log attached for a human

Notice CASE-06. The action always matches the certainty. A high-confidence single-policy fix opens a PR. A security-critical or storage change opens a draft for a human. An anomaly that won't reproduce on a fork becomes an issue — never a speculative patch. That restraint is what makes the green PRs trustworthy.

02 · What the six have in common

One fix shape, proven before it ships.

It returned 200.

Every case answered successfully. No stack trace, no alert, no log line that looks wrong — which is exactly why these bugs survive in production for weeks.

The frontend was the only witness.

A rage-click, a dead-click, an abandoned form, a "report a problem." The frustrated user is the signal your monitoring doesn't have.

The fix was a few lines of policy.

Not application code — insforge.toml. One predicate, one bucket rule, one claim path. Small, structured, reviewable.

It was tested on a real fork.

Prod still broke, the branch was fixed — measured in row counts. The replay delta is the proof stapled to the PR, not a promise.

03 · The line that holds it together

Sentry needs a stack trace. Hush doesn't.

It watches the session, correlates it to the backend request that failed it, replays that request on a forked InsForge backend, patches the policy, and opens the PR — before support sees the ticket.

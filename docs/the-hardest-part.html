Hush · engineering brief · 2026-06-06

The hardest part is making the system tell us when it's wrong.

Capture is plumbing. Diagnose is a prompt. The hard part is refusing to ship a confident-but-wrong PR. Every step can lie. The architecture is a layered defense against being lied to by ourselves.

01 · The obvious vs the actual

The first answer is the wrong one.

Ask "what's the hardest part of Hush?" and the natural answer is a specific component — the JWT forging, the branch project lifecycle, the LLM prompt. Each of those is fiddly engineering. None of them is the hardest thing.

// the obvious answer

A specific component is hardest.

"The JWT forging is the tricky bit." "The branch project lifecycle is racy." "The diagnosis prompt is finicky." Each is real but each is solvable in isolation by writing more careful code. None requires a structural answer.

// the actual answer

Keeping the system honest is hardest.

Every step can produce a plausible-but-wrong output. A wrong PR is worse than no PR — it burns the credibility the rest of the product depends on. The hardest engineering work is making the agent prefer "I don't know" over "I'm confident and wrong."

A wrong-fix PR is a worse failure mode than a missed-bug silence. Hush has to know when it doesn't know, because the entire product's credibility lives there.
02 · The five ways Hush could lie to itself

Each step has a confident-but-wrong failure mode.

If you map the loop and ask "where could this confidently produce a wrong answer that survives downstream checks?", you get exactly five places. Naming them is the first step to defending against them.

LIE 01 · CORRELATION

Wrong-request selection.

The user did 10 things in the session. 100 backend requests fired. We pick one as "the bug." If we pick the wrong one, we diagnose the wrong policy, propose the wrong patch, and everything downstream confidently builds on the lie.

// failure mode:
fix lands · wrong policy patched · real bug still there
LIE 02 · GROUNDING

Hallucinated schema.

The LLM proposes a TOML diff referencing a column or policy that doesn't exist. The patch looks reasonable. The branch project may even accept it. The replay tells us nothing because the column was never queried.

// failure mode:
PR opens · code references tenant_id_arr · column doesn't exist
LIE 03 · NO-OP PATCH

The patch doesn't change behavior.

The LLM emits a diff that looks like a fix but is logically equivalent to the original. The fork passes the replay only because the policy still filters nothing the user cared about. The verdict is a false positive.

// failure mode:
both prod and fork match · we declare "fix verified" · nothing changed
LIE 04 · ACCESS WIDENING

The patch fixes the symptom by removing the check.

The simplest way to make an RLS policy return more rows is to weaken the predicate. The LLM, under prompt pressure to "return more rows," may emit a diff that drops the tenant scoping entirely. Tests pass; security collapses.

// failure mode:
PR ships · access widened · cross-tenant data leak
LIE 05 · OVERFIT VERDICT

The fix passes one case and breaks others.

We replay the captured failing request. The fork passes. We declare the fix verified. But the patched policy now returns rows for sessions that should have stayed empty — a different RLS misfire we created while fixing the first one.

// failure mode:
demo bug fixed · neighboring test case now fails · regression shipped
LIE 06 · STALE FORK

The fork doesn't match prod's current shape.

Pre-warmed branch projects sit idle. Schema drifts on prod (a migration runs, an admin tweaks a policy in the dashboard). The fork's replay verdict no longer reflects prod behavior. We "prove" a fix against a backend that no longer exists.

// failure mode:
fork passes · prod shape diverged · verdict is fiction

Each lie is plausible. Each survives a casual review of the PR. Each ships a fix that looks right and is wrong. The architecture's job is to detect each one before the PR opens.

03 · The defenses, matched to each lie

Six failure modes. Six structural answers.

Each lie gets a specific defensive mechanism. None of these is "be careful." Each is something a deterministic check or a falsifiable signal enforces — because "be careful" is what teams say right before they ship a bad PR.

Failure mode The defense
01 · Wrong request The correlation helper returns one candidate or escalates to issue. Multiple plausible candidates → low confidence → no PR. Better silence than a wrong fix. functions/correlate.ts
02 · Hallucinated schema The diagnose prompt gets the current TOML slice for the implicated table, extracted live. The LLM can only reference columns that exist. functions/toml.ts
03 · No-op patch The verdict requires two independent signals: prod must fail AND fork must pass. A no-op patch makes the fork match prod, not differ from it. functions/replay.ts
04 · Access widening Deterministic post-LLM check: fewer conjuncts, looser claim paths, or removed scoping columns → flag widening → force-route to issue. functions/safety.ts
05 · Overfit verdict The branch project carries two seeded tenants. The replay covers both directions — the failing case must pass AND the neighboring case must not regress. Single-tenant replay is not enough.
06 · Stale fork Forks are provisioned fresh from prod at the moment of replay, not pre-warmed and held. The pre-warm pool exists for latency; the schema is pulled at apply-time, not at creation.

Every defense is referenced from a ticket in agents/inbox/. None of them is "add a comment to be careful."

04 · The principle

Two signals. One is not enough.

Every claim Hush ships has to be backed by two independent signals. One signal is a hunch. Two independent signals — neither derived from the other — is proof.

  • "The bug is real": the prod replay fails AND the user's session timestamps line up with the request window. One alone could be coincidence.
  • "The fix works": the fork replay passes AND the diff did not widen access. A passing replay alone doesn't prove the fix is safe.
  • "This patch generalizes": the failing tenant's request passes AND the neighboring tenant's request still fails to read the wrong rows. One direction proves nothing about the other.
  • "We're confident enough to PR": the confidence score is ≥85 AND the safety rail didn't flag the diff. The score alone can be wrong; the rail alone can pass a no-op.
// the rule

Every load-bearing claim in Hush has to be backed by two independent signals. When we have one, we drop a confidence tier. When we have none, we file an issue.

05 · Why this is harder than it looks

The temptation is to skip the second signal.

It is always faster to ship a PR backed by one signal. The replay passed — that's enough, right? The diff looks small — surely it's not widening. The correlation found a request — let's diagnose from there.

Every single-signal PR is plausible in isolation. The cost only shows up in aggregate, after the agent has been running for weeks and the false-positive rate is what it is. By the time you measure it, you've burned the trust the product was supposed to earn.

The discipline is to build in the second signal up front, even when you could ship without it. Because once a PR ships wrong, the next ten PRs are read with that suspicion. Confidence tiers and the safety rail aren't features — they're the product's right to exist.

This is also why the architecture leans on InsForge's primitives so heavily. Branch projects give us a second signal cheaply (the fork's verdict). insforge.toml gives us a structured diff we can validate deterministically. On a different substrate, every second signal would be expensive to compute, and we would skip them when budgets got tight.

06 · One sentence

What a technical judge should walk away with.

// the take-away

The hardest part of Hush isn't building the loop. It's building the loop so it refuses to lie — and on InsForge, that refusal is structurally cheap. On any other substrate, it's structurally expensive, which means most agents on other substrates will skip it.
